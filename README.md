# Game Point

**Where gamers connect.** A social platform for gamers to build a profile, find people who play what they play, battle, chat, and share their wins — for eFootball, Dream League Soccer, EA SPORTS FC, Call of Duty, Call of Duty Mobile, GTA V/Online, Need for Speed, and Asphalt.

This is a real, working full-stack application — every button in the UI calls a real API route that reads and writes a real database. It is **not** a static prototype.

## Quick Start

### 1. Install dependencies

```bash
npm install
```

### 2. Set up your environment

```bash
cp .env.example .env
```

Open `.env` and fill in:
- `JWT_SECRET` — any long random string (`openssl rand -base64 32`)
- `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` — from a free account at [cloudinary.com](https://cloudinary.com). Image uploads will fail without these, but the rest of the app works fine without them.
- Leave `DATABASE_URL="file:./dev.db"` as-is to use SQLite (zero setup).

### 3. Set up the database

```bash
npm run db:push    # creates dev.db and all tables from prisma/schema.prisma
npm run db:seed    # adds games, categories, and 3 demo accounts
```

### 4. Run it

```bash
npm run dev
```

Open [http://localhost:3000](http://localhost:3000).

**Demo login:** `demo1@gamepoint.demo` / `Demo1234!`

### 5. (Optional) Run tests

```bash
npm test
```

## Switching to PostgreSQL

The app was built on SQLite so you can run it with zero setup, but it's designed to move to Postgres in about 60 seconds:

1. In `prisma/schema.prisma`, change:
   ```prisma
   datasource db {
     provider = "postgresql"   // was "sqlite"
     url      = env("DATABASE_URL")
   }
   ```
2. In `.env`, set `DATABASE_URL` to your Postgres connection string, e.g.:
   ```
   DATABASE_URL="postgresql://user:password@host:5432/gamepoint"
   ```
3. Run `npm run db:push && npm run db:seed` again.

No application code changes are needed — all database access goes through Prisma.

## Upgrading messaging to real-time (Socket.IO)

Messaging currently works by polling `GET /api/conversations/:id/messages?after=<timestamp>` every 3 seconds from `app/messages/page.tsx`. This is real and functional, just not instant-push. To upgrade:

1. Add a custom Next.js server (`server.js`) that attaches a Socket.IO server alongside the Next request handler.
2. On message creation in `app/api/conversations/[id]/messages/route.ts`, emit the new message to the conversation's room instead of (or in addition to) relying on the client's next poll.
3. In `app/messages/page.tsx`, replace the `setInterval` polling loop with a socket listener.

The database schema and REST API don't need to change — this is purely a delivery-mechanism upgrade.

## Architecture

```
app/
  api/                REST API route handlers (the backend)
    auth/              register, login, logout, me
    users/[id]/        profile get/update, game selection, follow
    games/             list games + categories with live counts
    posts/             feed, create, like, comment
    battles/           create, list, join, accept, decline, cancel, report result
    conversations/     1:1 messaging (create, list, send/poll messages)
    notifications/     list + mark read
    players/           search/find players
    reports/           file a report
    admin/             stats + report moderation (admin-only)
    upload/            Cloudinary image upload
  (pages)              register, login, home, games, games/[slug], battles,
                       battles/[id], players, messages, notifications,
                       profile/[id], admin
components/            GameCard, PostCard, BattleCard, PlayerCard, Navigation
lib/                   db.ts (Prisma client), auth.ts (hashing/sessions),
                       cloudinary.ts, utils.ts (battle codes, JSON helpers),
                       admin.ts, useUser.ts (client hook)
prisma/                schema.prisma (full data model), seed.ts
middleware.ts          protects /home, /profile, /battles, /messages,
                       /notifications, /players, /admin behind auth
tests/                 Vitest unit tests
```

### Data model

`User` → `Profile` (1:1), `UserGame` (which games they play), `Post` → `PostImage`/`Comment`/`Like`, `Follow` (self-referential), `Conversation` ↔ `ConversationParticipant` ↔ `Message`, `Battle` → `BattleParticipant` → `BattleResult`, `Notification`, `Report`. See `prisma/schema.prisma` for the full picture — it's the single source of truth for how everything relates.

### Auth

Passwords are hashed with bcrypt (`lib/auth.ts`) — never stored in plain text. Sessions are signed JWTs stored in an `httpOnly` cookie (`gp_session`), verified both in `middleware.ts` (route protection) and per-request in API routes (`getSession()`).

### Battle codes

Real, collision-checked codes like `EF-7K92X` (game prefix + 6 random unambiguous characters), generated server-side in `lib/utils.ts` and validated against the database on join — not a fake frontend-only string.

## Becoming an admin

There's no signup flag for this on purpose. To make a seeded or created account an admin:

```bash
npm run db:studio
```

Open the `User` table in the browser UI that launches, find your account, and change `role` from `USER` to `ADMIN`. Then visit `/admin`.

## Deployment

This is a standard Next.js + Prisma app and deploys cleanly to:

- **Vercel** (recommended for the app itself) — connect the repo, set the environment variables from `.env.example` in the Vercel dashboard, and set `DATABASE_URL` to a hosted Postgres instance (Vercel Postgres, Supabase, Railway, Neon, etc. all work — SQLite's local file won't survive serverless deploys, so switch to Postgres first using the steps above).
- **Railway / Render** also work well if you want the app and database on the same platform.

Build command: `npm run build` (runs `prisma generate` automatically via `postinstall`). Start command: `npm start`.

## Original spec vs. this build

The original brief (kept in full in the project history) asked for a much larger surface area — tournaments, full WebSocket real-time everywhere, cloud-hosted dynamic per-game backgrounds, a complete admin CRUD suite, full SEO, and more. Building all of that to production quality in a single pass wasn't realistic, so this build focused on making the **core gameplay loop completely real and working end to end**: pick your games → build a profile → post → find players → battle → message → get notified. Everything in the table above marked ⏳ is a natural next slice on top of this same architecture — none of it requires a rewrite.
